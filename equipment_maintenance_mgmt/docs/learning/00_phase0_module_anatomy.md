# Phase 0: Environment & Module Anatomy

> Day 1 · ~1.5 h · Outcome: an empty but installable addon with the correct Odoo 19 structure.

## 1. LEARN

### 1.1 What is an Odoo module (addon)?
A Python package that Odoo discovers on the **addons path**. It is identified by a `__manifest__.py` and loaded by technical name (the folder name, here `equipment_maintenance_mgmt`).

When a module is installed or upgraded, Odoo:
1. imports its Python package, which registers the model classes in the **registry**;
2. creates or updates the **database tables and columns** for each model (`_auto_init`);
3. loads the XML/CSV **data files** in the order listed in the manifest, creating records such as views, menus, groups and access rights, each with an **XML ID** (`module.identifier`);
4. loads the **demo** files if the database has demo data.

### 1.2 The manifest keys used

| Key | Our value | Meaning |
|---|---|---|
| `name` | Equipment Maintenance Management | Display name in Apps |
| `version` | `19.0.1.0.0` | `<odoo series>.<major>.<minor>.<patch>` |
| `category` | `Services/Maintenance` | App category (`Parent/Child`) |
| `author` | Harsha Madushan | |
| `license` | LGPL-3 | Must be declared (warning otherwise) |
| `depends` | base, mail, hr, hr_hourly_cost, product | Installed first; their models/XML IDs become available |
| `data` | security → data → views → reports → menus | **Order matters**: a file can only reference XML IDs already loaded |
| `demo` | demo file | Only with demo data |
| `application` | True | Shown as an App with its own icon |
| `images` | banner | App store image |

### 1.3 Directory layout (Odoo coding guidelines)
See [coding/coding_standards.md](../coding/coding_standards.md). In short:
- `models/` is one file per main model, named after it.
- `views/` holds `<model>_views.xml` and `<module>_menus.xml`.
- `security/` holds `ir.model.access.csv`, `<module>_groups.xml` and `<model>_security.xml`.
- `data/`, `demo/`, `report/`, `static/description/` and `tests/` complete the structure.

### 1.4 Running Odoo for development (local install)
```
"D:\Odoo Server\V19\python\python.exe" "D:\Odoo Server\V19\server\odoo-bin" ^
   -c "D:\Odoo Server\V19\server\odoo.conf" ^
   --addons-path="D:\Odoo Server\V19\server\odoo\addons,C:\Users\Centrics\Desktop\Final Assestment" ^
   -d maint_eval --with-demo -i equipment_maintenance_mgmt --http-port=8069
```

| Option | Use |
|---|---|
| `-i module` / `-u module` | install / upgrade |
| `-d db` | database |
| `--with-demo` | load demo data in a new DB (Odoo 19 flag) |
| `--dev=xml,reload` | reload views/Python on change while developing |
| `--test-enable --test-tags /module` | run the module's tests |
| `--stop-after-init` | exit after install/tests (CI style) |

> The Windows service `odoo-server-19.0` already listens on port 8019, so the dev run uses `--http-port=8069`.

## 2. DESIGN
- Technical name `equipment_maintenance_mgmt`. This avoids clashing with Odoo's own `maintenance` app, and our models are prefixed `equipment.maintenance.*`.
- **Standalone** module (not extending `maintenance`), to show the full ORM, view and security skill set.
- Dependencies are chosen for the business need: HR (responsible employee, technician hourly cost), product (spare parts) and mail (chatter and to-dos).

## 5. REFLECT
| Pitfall | Lesson |
|---|---|
| Referencing a view or action before its file is loaded | Order `data` as: security → data → views → reports → menus |
| Forgetting `license` | Odoo logs a warning; always declare it |
| Using a name that already exists (`maintenance`) | Prefix technical names to avoid collisions |
